# Agent Instructions for Portale-von-Molthar

1. Always use Python 3.11+ syntax and features; always make sure files and project can still be imported and have valid syntax. Never place class or instance methods outside of their class definition. All methods must be defined within the appropriate class body as required by python3.11+.
2. Always respect coding rules induced by ruff, see which ones in the pyproject.toml. This includes sorting imports. This includes line length. Exceptions are allowed according to the pyproject.toml. Respect empty lines in the same way as they are enforced by ruff.
3. Always use type hints for function arguments and function return values. It must be compatible with mypy. Define a TypeAlias whenever it makes code more readable. Never use a TypeAlias in an isinstance check.
4. Always respect coding rules induced by bandit.
5. Always follow the pylint rules enforced by the pyproject.toml, i.e., only meaningful variable names with at least three characters. `_` is allowed. Other pylint rules are enforced via ruff.
6. Always follow the flake8 and flake8-errmsg rules enforced by the pyproject.toml, i.e., only the EM check set without EM101. Other flake8 rules are enforced via ruff. When running flake8, do not pass `--config pyproject.toml`; use `flake8` with `flake8-pyproject` installed.
7. Always write docstrings in Google style. Do not include type information for arguments or return values in the docstring if the type is already specified in the function signature. The order of the sections is Args, Returns or Yields (if present), Raises (if present), Examples (if present), Notes (if present). 
8. Docstrings can be inherited for a method from the parent class. Escape the ruff check and mark it with a comment, e.g., `# noqa: D102  # docstring from parent`.
9. For docstrings and comments, explain the purpose, arguments, and return values, especially for scientific and tensor operations. For tensor operations, explain the leg ordering of input arguments and return values.
10. Always check if a class has a parent class when working on a class; this is visible via the class definition in the first line of the class. If implementing or changing methods of a class, always check if the method is defined in the parent class and ensure the same arguments are named the same. Ensure other children in the same repository are modified if necessary.
11. Always check if a class has a parent class when working on a class; this is visible via the class definition in the first line of the class. If implementing a new methods in a class which has a parent class, always make the method either private by a leading underscore or implement a compatible interface in the parent class and in all other children of the same repository.
12. When adding new features, ensure they are modular, well-documented, and tested if possible.
13. When drafting code in chat, avoid repeating unchanged code; use comments like ...existing code... to indicate omitted regions. Do not add these comments to files.
14. Always check the latest file contents before making edits, as files may be changed by other tools or users.
15. If unsure about code generation, ask to clarify the question.
16. If classes define regions (indicated by "# region" and "endregion" compatible with VSCoode), always respect these regions. For example, magic methods go into the region for magic method sorted alphabetically. Always make sure the order is the same for the parent as for child class if the child class overwrite a method.
17. Abstract methods with decorator do not raise NotImplementedErrors. Always use the decorators like `abstractmethod`.
18. Tests go into the tests subfolder. Then, the folder follows the same structure as the module. Each test function name has the prefix test_ followed by the function or method name to be tested, followed by other specifications if needed. A function `my_addition` in `src/portale_von_molthar/additions/add.py` would be tested in `tests/additions/test_add.py` in a test function named `test_my_addition`.
19. Use `@pytest.mark.parametrize` as well to iterate over arguments of methods that are tested within the unittest, e.g., methods, orders of approximations.
20. If unittests are defined for abstract classes, they always have to test all children classes implementation (the test file of the children class can skip testing abstract methods). This requires the test function to start with `def test_something(xx: type[ParentClass], ...)` used together with the decorator `@pytest.mark.parametrize` setting the different children classes.
